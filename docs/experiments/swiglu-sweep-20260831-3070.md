## 关键观察（"为什么赢 / 为什么输"）

### Triton 相对赢区（M/K 中等）
- M=2048 × K=768 × F=3072: **1.176x**（全 sweep 第二快）
- M=256/1024 × K=768 × F=3072: 1.10x / 1.05x
- 模式: K=768、M≥256 时 Triton tiled matmul 能接近/略超 cuBLAS FP32；K=4096 大 F 时落后

### 失败案例（最有价值）
1. **cuda/cutile 大 shape 严重落后**: eager M=1024×K=4096×F=11008 = 31.7ms，cuda = 287ms（0.11x）、cutile = 346ms（0.09x）。
   原因假设(待 profile 验证): \`matmul_tiled_auto\` dispatch 在 (M,4096→11008) 这类大 N 上 tile 配置差 / 未走 TensorCore（strict FP32 下 TF32 关）+ 第 3 层 GEMM (F,K) 非连续。
2. **compile 在 3070 上恒慢**（0.065x~0.97x）：Inductor 生成 kernel 未跑赢 cuBLAS，且小 M 时 Python/launch 开销显著。
3. **concat 大多劣于 eager**（0.43~0.80x）：合并成单次 (M, 2F) GEMM 在内存带宽上不划算，仅 decode M=4/16 微胜。

## fp16 现状
- eager/concat/compile: 可跑，norm_l2 ~5e-4（合理）
- triton/cuda/cutile: **全部 dtype 边界报错**（tl.dot 同 dtype / A must be float32 / ct.mma 同 dtype）
- fp16 性能主线（TensorCore）尚未跑通 —— 这是下一个优化阶段的重点

## 下一步（建议）
1. **fp16 支持**: 给 triton matmul 加 input_precision=ieee 或 fp16 输入路径；给 CUDA 加 fp16 matmul（已有 WMMA）
2. **cuda/cutile 大 shape 诊断**: ncu profile 确认 dispatch/tile/tensorcore 瓶颈
3. **decode 小 M 专项**: M=1/4 时 0.1-0.5ms 的差距来自 launch overhead vs kernel 效率，可试 persistent kernel

## 更新（2026-08-31 晚）：fp16 TensorCore 路径打通 —— v2 第一条稳定性能胜势

### 做了什么
- `triton_kernels/matmul.py`: tl.dot 支持 fp16/bf16 输入（input_precision + fp32 累加器，fp32 保持原路径）
- `triton_kernels/swiglu_triton.py`: sigmoid 在 fp32 计算后回落（Triton tl.sigmoid 不支持 bf16/fp16）
- commit `4118882`; 验证 fp16 norm_l2=4.7e-4, bf16=3.8e-3（17 项 triton 测试全过）

### 赢 / 输边界（v2 核心问题的最清晰回答）
- **赢区**: prefill/train (M≥128)。K=768 系列 M≥512 达 2.9-3.9x；K=4096 大 shape M≥128 稳定 3.0-3.2x
- **输区**: decode 小 M (M≤32) 全程 0.5-0.6x —— 多次 kernel launch + autotune 开销压倒 TensorCore 收益
- triton-fp16 vs eager-fp16: M≥128 时 1.03-1.23x（同等 dtype 下仍略有胜），decode <1x

### 下一步（由此数据决定）
1. **decode 小 M 专项**: 小 M 时 Triton 输在 per-kernel launch —— 融合成单 kernel（gate+up 一次 GEMM + epilogue SiLU×up + down GEMM 或 persistent kernel）应是主要方向
2. **cuda/cutile 接 fp16**（binding 暴露 WMMA）有望在 M≥512 也到 2-3x，但 decode 仍受制于同样 launch 问题
3. **TF32 对照**: strict FP32 下 triton 只 0.8-1.2x，fp16 是其 3x —— 说明 3070 上 TF32/FP16 TensorCore 是唯一性能杠杆

### 更新 3（2026-09-01）：cuda 0.1x 根因确认 —— 主动精度取舍，非无意识失败

**软件拆段测时（M=1024,K=4096,F=11008, fp32）**:
- gate 91.7ms / up 91.7ms / down 92.0ms（三个 GEMM 均匀慢），swiglu 0.35ms（正常）
- 单个 eager (cuBLAS) GEMM = 21ms → **自定义 CUDA matmul 比 cuBLAS 慢 4.4x**

**根因（kernels/mlp/matmul.cu setTimeout dispatch 注释原文证据）**:
```
max_dim >= 1024: 改 matmul_tiled + Kahan 路径.
原因: WMMA64 FP16 mma 累加 L2 偏差 0.75 vs cuBLAS-FP32,
Kahan/split 均无法改 wmma64 路径 (PTX 层级 O(eps) 累加).
改 path 是唯一可控修复. Perf trade-off: 大尺寸丢 2-3x FP16 TensorCore 加速, 接受.
```
即：**cuda 后端为 strict FP32 精度主动放弃 TensorCore，改走 32x32 小 tile + Kahan**。91ms 是小 tile 在 (1024,4096,11008) 上 occupancy/复用不足的结果。

**结论（闭环 v2 的 cuda 失败案例）**:
- cuda 0.1x 不是 bug，是**精度→放弃 TensorCore 的已文档化取舍**
- 真正的修复 = WMMA FP16 精度 bug（L2 偏差 0.75）→ 属于需要数值研究的新优化，非本轮范围
- 与 triton 对照：triton（fp16 input_precision）在 strict FP32 下用 FP32 累加器无此 bug，且能走 TensorCore → 这就是 triton fp16 3x 而 cuda 0.1x 的根本差异

### 更新 4（2026-09-01）：decode 摊销验证 —— multi-token 是 decode 赢法的本质

K=4096, F=11008, fp16, per-token 成本 vs batch M（RTX 3070）:

| M | per-token eager16 | per-token triton16 |
|---|---|---|
| 1 | 0.827ms | 0.751ms |
| 8 | 0.094ms | 0.095ms |
| 32 | 0.024ms | 0.024ms |
| 128 | 0.010ms | 0.010ms |

- **M=1→128，per-token 成本降 ~80x**（权重读摊销）
- triton-fp16 在 M=64 达 0.83x（优于 eager），其余 ~1.0
- 结论: decode 场景若用大 decode batch（continuous batching 语义），per-token 成本可摊销 80 倍；
  单 token decode 受 3070 HBM 带宽物理限制（~0.75ms/token）。

### 更新 2（2026-08-31 深夜）：decode 融合 kernel 负结果 —— 证明 decode 小 M 是权重带宽 bound

尝试: "fused gate+up GEMM + SiLU×up epilogue"（`triton_kernels/fused_swiglu_gateup.py`，1 launch 替代 3 launch，commit 待推）

**结果: 融合后反而更慢**（fused/tr16 = 0.69x, vs eager-fp32 0.83-1.15x）

| shape | eager-fp32 | triton-fp16 | fused-fp16 | fused/e32 |
|---|---|---|---|---|
| 1×768×3072 | 0.097 | 0.081 | 0.118 | 0.83x |
| 32×768×3072 | 0.135 | 0.081 | 0.118 | 1.15x |
| 1×4096×11008 | 3.42 | 1.41 | 4.29 | 0.80x |

**根因（已验证）**:
1. fused kernel 时间与 M 无关（0.118ms 固定）→ 瓶颈不是 launch，是**权重读取带宽**：
   768×6144×2B = 9.4MB / 0.118ms ≈ **80GB/s**；K=4096 时 180MB / 4.29ms ≈ **42GB/s**
2. **单 token decode 必须每次重读全部权重**（3070 HBM ~250GB/s 上限）→ 融合只省 launch，省不了权重带宽
3. eager（cuBLAS）M=1 时 0.097ms 读 18.9MB (fp32) = 195GB/s，权重复用效率更高

**结论（v2 重要）**: decode 小 M 是 **memory-bound（权重读）而非 launch-bound**。融合 kernel 在 3070 上无效。
真正方向: (a) 多 token batch 摊销权重读（=prefill）; (b) 权重驻留 L2/shared 的 persistent 多 token kernel;
(c) 接受 3070 单 token decode 的带宽物理上限，把 decode 性能故事移到 3080 Ti/3090 Ti 或 5070 Ti。
保留 fused kernel 源码（有正确性，norm_l2 2e-4），用作"负结果"证据与控制变量。
